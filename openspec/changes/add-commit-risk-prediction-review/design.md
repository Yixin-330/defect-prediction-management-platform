## Context

当前仓库只有规划与汇报产物：`backen/`、`fronted/` 均为空目录，`openspec/specs/` 为空，尚无任何代码或已确认的技术选型。产品需求、产品主线、分工和技术架构已完成设计（见阶段汇报 02–06 页及 `projects/jit_course_report_ppt169_20261009/notes/`），架构已明确五个模块：前端、后端、数据存储、数据处理、预测模型，以及离线训练与在线预测两条链路。

本设计需要解决的约束：

- 组内四名成员按数据、模型、后端、前端分工推进，各模块需要能独立开工又能尽早联调。
- 阶段汇报"当前问题"明确指出三点：首个可用版本范围不清、模型实验工作量大、模块间数据格式/特征顺序/模型文件/接口结构未对齐。
- 技术栈按团队最终选型确定，尚未确认；本设计中的框架与存储选型为**待确认默认值**，需在实现前由团队确认。
- 阶段汇报"禁止"条目明确：不得出现未经确认的效果指标、进度百分比、技术栈和日期。文档与界面均受此约束。

## Goals / Non-Goals

**Goals:**

- 让"提交 → 风险评分 + 解释 → 审查安排 → 处理记录"这条链路在课程项目上端到端跑通。
- 用**一份**特征定义与**一份**特征提取实现同时服务离线训练与在线预测，从结构上排除特征规则分叉。
- 用公共样例数据把四个模块的输入输出契约在真实仓库与真实模型就绪之前固定下来，使四名成员可以并行开工。
- 让模型产物（模型文件 + 元数据）成为离线与在线之间唯一的交付接口。

**Non-Goals（设计层面）：**

- 不做多租户、权限体系与登录认证。首个版本按单团队、共享环境设计，用户身份在审查记录中以"处理人"字段自由填写而非账号。
- 不做实时推送或 Webhook 触发的自动预测。预测由用户或脚本显式发起。
- 不做模型在线学习、增量训练或自动重训。
- 不做课程项目规模的模型效果承诺；评估结论仅在开源数据范围内陈述。
- 不做 8 模型矩阵全部达标作为交付门槛，基线先行。

## Decisions

### D1. 特征契约单一来源

以一份**特征定义文件**（特征名、顺序、含义、缺省值、计算依赖）作为唯一真源，离线特征构建与在线特征提取都从该定义生成输出。离线与在线共用同一个特征提取函数，在线路径通过限制可访问的历史范围（只暴露目标提交及其之前的仓库状态）来保证不使用未来信息，而不是另写一套简化特征。

- 备选：离线用完整历史、在线用轻量特征。放弃原因：会造成训练/预测特征分布不一致（training-serving skew），且难以发现。
- 备选：只写离线，在线侧由后端按需自行计算。放弃原因：违反 specs 中"训练与预测共用特征规则"的要求。

### D2. 时间序列划分，而非随机划分

训练/验证/测试按时间顺序切分，测试集整体晚于训练集。这既避免未来信息泄露，也与在线预测的真实场景（预测当下提交、不看未来）一致。

- 备选：随机划分或交叉验证。放弃原因：会引入未来信息，使评估结果偏乐观，掩盖真实可用性。

### D3. 模型产物的交付接口 = 模型文件 + 元数据文件

模型持久化时同时保存：模型文件、特征顺序、特征含义、训练数据范围（时间区间与项目）、划分方式、随机种子、两类评估指标摘要、模型类型。在线服务只依赖元数据中的特征顺序对齐输入，不依赖任何训练侧代码。

- 备选：只保存模型权重，特征顺序写在代码常量里。放弃原因：一旦特征定义变更，模型与在线特征的错位会静默发生。

### D4. 风险评分的对外表示

对外返回**校准前的模型输出**（0–1 区间的风险分）加上由阈值映射得到的**优先级分档**（高/中/低），并同时返回模型标识、预测时间与解释可用性标志。分档只用于排序和界面区分，不解释为缺陷概率或准确率。

- 备选：只返回分档。放弃原因：分档阈值未定，只返回分档会让阈值调整牵动接口。
- 备选：对外称之为"缺陷概率"。放弃原因：开源数据上未经校准，该表述会构成未经确认的效果承诺。

### D5. 审查状态机显式建模

状态集合为 `待审查 → 处理中 → 已处理`，另有终态 `已忽略`（用于判定为无需审查的项）。仅允许 `待审查→处理中`、`待审查→已忽略`、`处理中→已处理`、`处理中→已忽略`；对同一提交重复创建不产生新项。状态转移在服务端校验，非法转移返回明确错误。

- 备选：用自由文本状态字段。放弃原因：无法拒绝非法流转，也无法做状态筛选。

### D6. 模块边界与接口形态

- 后端对外提供资源式接口：项目、提交、预测结果、审查项四类资源，路径与响应字段以 specs 中的可观察行为为准。
- 后端不直接承载模型推理逻辑，而是通过**预测调用边界**（进程内调用或独立预测服务）访问模型；首个版本允许同一进程内加载模型以降低联调成本，边界保持可替换。
- 前端只通过后端接口取数，不直接访问数据库或模型。

技术栈默认值（**待团队确认**）：后端 FastAPI，前端 Vue + ECharts，存储 PostgreSQL（开发期可用 SQLite），部署 Docker + GitHub Actions。此默认值来自分工表中各成员的技能侧重，非已确认选型。

### D7. 公共样例数据的形态

提供一份小型合成样例：若干提交记录、对应的 14 维特征、SZZ 标签，以及一份预期的样例预测响应与样例审查记录。样例数据随附说明文档，包含字段含义与重建方式。四名成员以此为联调基准，不依赖真实开源数据集下载或真实模型训练完成。

### D8. 与既有产物的关系

本设计只定义新增功能。产品文档与阶段汇报材料不改动；`openspec/specs/` 在归档时由本变更的 delta 生成五个新能力的主 spec。

### D9. 开发初期的三部分契约与确认规则

开发初期先共同确定三部分：前端与后端、模型与后端、数据处理与后端及模型。以下接口优先方案已确认作为讨论与联调基线；标为“待共同确认”的具体字段、枚举与参数不得当作团队已经定稿的契约。技术栈仍按 D6 待确认，不因本节采用 HTTP、JSON 或函数签名而视为已选定框架。

| 契约 | 共同确认人 | 交付与验收 |
| --- | --- | --- |
| 前端 ↔ 后端 | 张欣悦、侯洁；全员评审 | 路径、方法、字段类型与必填性、枚举、分页排序、错误与样例一致 |
| 模型 ↔ 后端 | 张艺馨、侯洁；白沁禾确认特征兼容性 | 模型包可加载，以公共样例完成预测；版本不兼容与模型加载失败明确报错 |
| 数据处理 ↔ 后端、模型 | 白沁禾、侯洁、张艺馨 | 共用特征定义与提取实现；训练和在线特征逐维一致，标签不进入在线输入 |

三部分共同约定：`project_id` 为后端分配的不透明字符串；`commit_sha` 为仓库返回的完整提交哈希，不以短哈希作为关联键；提交身份为二者组合。跨边界时间采用带时区的 ISO 8601 字符串，传输统一 UTC，前端按展示时区转换。业务字段采用 `snake_case`。分别记录接口版本、特征契约版本、数据版本和模型版本，不能用一个版本号替代全部兼容性判断。

契约定稿须包含字段类型、单位、取值范围、必填或可空、缺省规则、错误条件和样例。样例使用合成数据并明确标注，不作为真实模型效果。契约改变时由受影响模块共同确认，更新版本与样例；不可兼容变更不得静默上线。

### D10. 前端与后端契约

采用 HTTP + JSON，统一前缀 `/api/v1`。前端只依赖后端返回的业务对象，不直接拼装模型输入。首版交互采用单提交同步预测，不额外引入异步任务系统；超时显示失败并允许查询已有结果后重试。若实际耗时需要任务化，须重新共同确认调用契约。

下表是接口草案，具体路径、字段和枚举**待共同确认**：

| 方法与路径（省略前缀） | 输入 | 输出与用途 |
| --- | --- | --- |
| `POST /projects` | `name, repository_url, branch` | 登记项目，返回 `project_id` 与项目信息；仓库接入方式按 Open Questions 确认 |
| `GET /projects` | 分页参数 | 项目集合 |
| `GET /projects/{project_id}/commits` | 分页参数 | 按提交时间倒序返回提交集合 |
| `GET /projects/{project_id}/commits/{commit_sha}` | 路径标识 | 元数据、变更文件及最新预测；无预测时 `latest_prediction=null` |
| `POST /projects/{project_id}/commits/{commit_sha}/predictions` | 路径标识 | 执行预测，持久化并返回预测对象 |
| `GET /projects/{project_id}/predictions` | 分页、可选 `commit_sha` | 历史预测；每次成功预测具有独立 `prediction_id` |
| `GET /projects/{project_id}/risk-ranking` | 分页参数 | 每个提交取最新成功预测，按风险降序；同分时按提交时间、哈希稳定排序 |
| `POST /projects/{project_id}/reviews` | `prediction_id` | 创建审查项并保存对应评分快照；同一提交重复创建返回已有项 |
| `GET /projects/{project_id}/reviews` | 分页、可选 `commit_sha, status` | 审查记录集合 |
| `PATCH /projects/{project_id}/reviews/{review_id}` | `expected_version, status, handler, conclusion, notes` | 校验 D5 状态流转，原子更新记录与历史；并发版本不一致返回冲突 |
| `GET /projects/{project_id}/risk-trends` | `from, to, bucket` | 按提交时间统计风险分布与高风险数量，同时返回样本数量和数据是否充足 |

提交对象至少包含 `project_id, commit_sha, author, committed_at, message, files, lines_added, lines_deleted`；预测对象至少包含 `prediction_id, project_id, commit_sha, risk_score, priority, model_id, model_version, feature_schema_version, predicted_at, explanation`。`risk_score` 为有限数且位于 `[0,1]`，含义遵循 D4。优先级由后端按模型元数据中的阈值映射，并随预测记录保存阈值版本，前端不自行推导。

解释对象草案为 `available, reason, contributions`。可用时，贡献项含 `feature_name, direction, magnitude`；`direction` 拟采用 `increase/decrease/neutral`，`magnitude` 为非负的相对大小，具体归一化定义由模型方确认并写入元数据。不可用时 `available=false`、`reason` 非空、`contributions=null`；评分仍可有效返回。模型本身不可用则整个预测失败，不返回评分。

审查对象至少包含 `review_id, project_id, commit_sha, prediction_id, risk_score_at_creation, status, handler, conclusion, notes, created_at, updated_at, handled_at, version`。状态拟采用 `pending/in_progress/resolved/ignored`，分别映射 D5 四个状态；结论类型集合**待共同确认**。`resolved` 必须提交合法结论与处理人，处理时间由服务端生成。重预测不覆盖创建时评分；当前评分通过最新预测单独获取。

统一响应草案：成功为 `{data, request_id}`；集合的 `data` 为 `{items, page, page_size, total}`；错误为 `{error: {code, message, details}, request_id}`。分页拟采用从 1 开始的页码，默认每页 20 条、上限 100 条，具体值待确认。错误使用非 2xx 状态：参数不合法 400、资源不存在 404、状态或版本冲突 409、不可提取特征 422、模型不可用 503、内部异常 500；`code` 为稳定机器码，前端不解析错误文案。错误不包含伪造评分或内部堆栈。

趋势查询拟采用左闭右开的时间范围，每个提交仅计入最新成功预测，返回实际覆盖提交数；分桶时区、粒度与数据充足阈值待共同确认。不同模型或阈值版本的数据须区分展示或提示差异，不能无说明混成同口径趋势。

### D11. 模型与后端契约

首版通过进程内预测适配器调用，与 D6 的可替换边界一致；后端负责资源查找、特征获取、结果持久化、优先级映射和 HTTP 错误转换，模型模块负责产物加载、训练所得预处理、评分与解释。后端不自行重写标准化、缺失值插补或模型逻辑。独立预测服务会增加部署与通信成本，留作边界替换方案。

内部调用草案为 `load_model(bundle) -> ModelInfo`、`predict(feature_record) -> ModelPrediction`，名称及语言类型待共同确认。输入包含提交身份、`feature_schema_version` 和具名原始特征；适配器按元数据顺序组装向量，校验维数、字段集合、类型与有限数值。禁止只传无版本、无特征名的裸数组。模型输出包含 `model_id, model_version, risk_score, explanation`；内部输出与外部预测资源由后端映射，不要求模型认识数据库或 HTTP。

模型交付包必须包含：

- 模型文件及训练时拟合的预处理产物；预处理无需使用时显式声明。
- 元数据：模型标识与版本、模型类型、特征契约版本、特征顺序与含义、预处理说明、运行依赖、产物校验信息、评分语义、优先级阈值及其版本、解释方法与贡献大小定义。
- D3 规定的数据范围、划分方式、随机种子、数据版本和两类评估指标摘要，以及可复现的实验配置。
- 一份公共样例输入及对应输出检查规则；真实模型数值按约定容差检查，固定模拟响应仅用于接口联调并须明确标识。

序列化格式与依赖版本待模型方和后端方共同确认，不预先锁定某种模型库。上线前先校验产物完整性、特征兼容性和样例推理，再启用该版本。保留历史预测使用的模型版本，替换模型不重写旧结果。

失败分类至少包括 `MODEL_UNAVAILABLE`、`FEATURE_SCHEMA_MISMATCH`、`INVALID_FEATURES`、`INFERENCE_FAILED`；模型错误不得降级成默认评分。解释失败可以降级为显式的解释不可用，不能隐瞒评分失败。兼容性不通过时拒绝使用模型，不能靠补零、截断或猜测顺序继续预测。

### D12. 数据处理与后端、模型契约

数据模块负责仓库解析、原始特征计算、历史标签、清洗记录与数据集交付；后端负责在线流程编排及业务持久化；模型模块消费版本化数据集并拟合模型和预处理。数据模块不向前端提供另一套接口，模型不直接依赖业务数据库表结构。

| 边界 | 输入草案 | 输出草案 |
| --- | --- | --- |
| 后端 → 数据处理 | 仓库引用、分支、提交身份或解析范围 | 提交记录、逐条解析告警和处理摘要 |
| 后端 → 共用特征提取器 | 目标提交与受限历史上下文 | `FeatureRecord` 或明确的提取失败 |
| 数据处理 → 模型 | 指定数据版本与时间划分配置 | 训练/验证/测试样本、划分清单、特征定义、标签规则、审查工作量与处理摘要 |

`FeatureRecord` 草案包含 `project_id, commit_sha, feature_schema_version, extractor_version, history_boundary, features`，其中 `features` 为 14 个具名原始特征。特征定义文件是名称、顺序、含义、类型、单位、范围、缺省值及适用条件、计算依赖的唯一真源；14 维逐项计算口径、合并提交和空提交处理、缺省规则**待共同确认**，本设计不猜测具体取值。可按缺省规则处理的历史缺失与不可提取的错误应区分记录，不能把任何异常都转换为零。

`history_boundary` 记录目标提交及允许访问的历史边界，计算只能访问目标及其之前的允许历史；同一边界用于离线和在线，不能只靠时间过滤允许混入未来提交。缓存至少按提交身份、特征契约版本、提取器版本与历史边界区分，防止规则升级后复用旧特征。

离线样本在特征记录之外包含 `label`、标签生成截止时间、标签规则版本和审查工作量。SZZ 标签在观察截止时间未发现后续修复时按现有 spec 记为否定标签，同时保留截止时间以说明观察限制；在线输入不含 `label` 或未来修复信息。工作量口径、数据文件格式、划分清单结构及同时间提交的边界处理待共同确认，确保划分无提交重叠且时间区间严格有序。

原始特征计算与标签生成由数据方负责；标准化、编码、采样等训练步骤由模型方负责，其中需要拟合参数的步骤只能在训练集拟合，并将推理所需产物随模型交付。离线训练与在线预测都从原始特征进入同一套模型预处理，防止重复标准化或训练/预测口径不一致。

持久化采用显式的数据访问边界，不让各模块各自维护同一张表的写入规则。数据库结构、批量导入和事务方式待数据方与后端方确认；对外交付首先稳定业务记录结构，避免绑定具体数据库。

三部分联调完成条件：使用 D7 公共样例比对提交身份、字段与版本；同一提交离线/在线原始特征逐维一致；预处理及模型包可加载；预测可持久化、展示并转为审查项；重预测后审查快照不变。必须覆盖无预测、解释不可用、模型不可用、版本不匹配、特征失败、非法状态和并发冲突。对应 tasks 1.2–1.4 的文件与样例仍须实际交付，写入本设计不代表这些任务已完成。

## Risks / Trade-offs

- **开源项目与课程项目在规模、提交习惯上存在差异** → 评估结论显式标注适用范围；课程项目试用作为独立阶段开展，不用开源结果替代。
- **8 模型 × 两类指标实验量大，可能拖慢首个可用流程** → 基线先行：先跑通 1 个基线模型 + 两类指标 + 全链路，再逐个扩展模型；评估报告记录已覆盖模型数，不预设结论。
- **特征规则分叉（D1 的核心风险）** → 共用同一提取实现；增加"同一提交离线/在线特征逐维一致"的自动检查作为回归测试。
- **SZZ 标签本身是近似，存在误标** → 标签只用于训练与评估，不对外暴露为结论；评估报告说明标签生成方式与其局限。
- **模型或解释能力不可用时被伪造为有效结果** → specs 已要求返回明确错误、界面明确标注解释不可用；在服务层禁止返回占位评分。
- **阈值映射（D4）引入主观性** → 阈值集中配置并随模型元数据保存，调整阈值不影响接口形状；界面表述限定为"优先级"而非概率。
- **技术栈未确认导致返工** → 模块边界（D6）按接口而非框架定义；公共样例数据与接口契约先行，实现层替换成本受控。

## Migration Plan

- 无历史数据需要迁移，本次为从空目录新建 `backen/`、`fronted/` 的首个功能。
- 交付顺序按阶段汇报第四页"下一步计划"：先协作规范与样例数据 → 数据与模型基线 → 系统联调 → 课程团队试用。本变更覆盖到"系统联调"形成可运行完整流程为止，试用与反馈属于后续变更。
- 回滚策略：本变更不修改任何既有产物，回滚等价于不合并新增目录与本次 spec 归档。
- 归档时由 `openspec archive` 将五个 delta 写入 `openspec/specs/`，形成能力主 spec。

## Open Questions

- 技术栈最终选型（后端框架、前端框架、图表库、数据库、部署方式）—— 团队确认后填入实现；不影响 specs 与任务分解，因为模块边界按接口约定。
- 风险分档阈值取值（高/中/低的分界）—— 待基线模型评估结果出来后确定；不改变接口形状与规格。
- 是否需要账号体系与角色区分（学生/项目负责人/教师）—— 首个版本以"处理人"字段替代；若后续引入认证，属于新变更。
- 课程项目仓库的接入方式（本地路径、远端克隆还是平台 API）—— 影响接入实现细节但不影响提交读取与预测行为规格；联调前确认。
